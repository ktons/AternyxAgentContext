# 开发执行流程

- 执行用户明确指定的已有 roadmap；普通开发遵循 `AGENTS.md`，已有计划本身不构成执行授权。
- roadmap中还有未拍板的决策点时应先提醒用户，如果用户继续要求执行则按roadmap建议来。
- 应尽可能完成roadmap, 避免执行过程请示用户，无登记建议时按工程惯例/主流做法自行决策，并纳入汇报。
- 不执行依赖其他平台环境的任务，roadmap标记"无法验证", 在模块文档登记为远期事宜并告知用户，不影响整轮迭代收工。

## 角色与调度

- 主 agent 负责范围、派发、关键 diff 与证据审查、状态、Git 和交付；实现子 agent 负责实现、自验证、
  模块文档同步与摘要，不自行领取下一任务或操作 Git。只读 agent 提供事实、风险和证据。
- 同一工作区实现/修复串行，独立只读工作可并行；构建、GPU、运行实例统一调度。
  每次派发（含失败/中断接手与修复）用新子 agent，保持上下文干净。
- 构建、全量测试及已知长任务后台运行，保留日志和结果入口，主会话保持响应。

## 执行循环

1. **明确任务**：核对最新指令、分支、已有改动和依赖，领取当前迭代已满足依赖的 pending 任务，执行过程按依赖和 ID 推进。
2. **信息收集**：收集实现所需信息，精确到代码行号，避免子agent从头了解。收集时按架构入口 → 相关模块文档 → 必要源码。
3. **派发**：内联目标、边界、约束、已知结论、代码锚点、现状和验收；[派发与交接模板](references/task-brief.md) 按需裁剪。
4. **实现与自验证**：完整增量能独立编译和验收。C++ 用 `project-workflow` 编译受影响 target、跑 suite；
   行为敏感补目标证据，中性渲染用 `acceptance-verify`；纯文档只查差异、引用和规则，不构建引擎；
   图形开发则视觉验证，使效果符合预期。涉及c++数学任务时，应尽可能降低ulp, 但不追求0ulp，4~8 ulp尚可接受。
5. **审查与验收**：单项任务由主 agent 核对范围、关键 diff、知识同步和验证输出；整轮迭代完成后派新独立只读
   reviewer，根据意见做最终收尾，查缺补漏。缺证据先补，不因测试绿省略语义审查，也不无理由重跑通过项。
6. **登记与提交**：每个通过的完整增量更新 roadmap 状态与记录，再由主 agent 按 `AGENTS.md` 提交。
   未过验收派新的子agent继续迭代。禁止 push，分支/合并由用户发起。
7. **续作或收口**：未完部分带现状交新 agent；完成时确认自起进程回收，回报变更、验证、提交与遗留。
8. **文档沉淀**：模块机制/契约/缺陷同步模块文档，工具经验更新对应 references，可由子agent迭代时完成；`documentation-writing`。

## roadmap 状态与生命周期

- `docs/iteration/roadmap.md` 唯一记录当前迭代的任务状态、决策和执行记录；对应计划文档只存需求、
  设计约束、代码锚点、验收与风险。
- 当前迭代为“无”不凭空领任务；新普通需求走 AGENTS 通用流程。
- 执行中因实际情况或用户新指令需要插入/追加任务时，直接登记进当前 roadmap（新任务 ID、依赖、
  验收与依据），按同一执行循环推进；不重启规划、不另开 roadmap、不回到 `complex-task-planning`。
- 执行记录写任务 ID、日期、轮次、结果、可复制命令/suite、有意外情况计入备注。
- 完整收口核对需求、排查处置、验收与知识同步，删除本期计划，roadmap 重置为空模板一并提交。历史留 Git，不另造永久迭代总结。

## 失败与中断

- crash、停滞、证据矛盾保留现场，串行派专项新 agent排查。`win-crash-debug`,`graphics-debug-methodology`。
- 单次任务子agent派发，后台定时90分钟，超出时间算任务失败（常见子agent注意力耗尽），发消息给子agent要求停止并交接，之后派新的子agent继续实现。
- 单项任务连续三次派发仍未完成任务，由主agent判断问题复杂度，确认无法解决则中断整轮迭代，向用户详细汇报问题，避免在系统性问题的计划上继续消耗。
- 用户取消后保留交接并停止；等待用户明确授权开发时再恢复，恢复后剩余任务持续推进，不在索要授权。
