# 文档编写与维护

本技能约定模块文档的章节结构，以及设计文档、开发文档等一次性文档的落位与写法。
编写模块文档时，先从架构总览定位所属模块，再读模块文档，并用必要源码核对当前事实。

## 文档类型与落位

文档总目录为 `.agents/docs/`；架构总览固定为 `.agents/docs/overview-architecture.md`，作为文档入口。

| 类型 | 用途 | 位置 | 生命周期 | 模板 |
|---|---|---|---|---|
| 模块文档 | 维护模块当前事实 | `.agents/docs/modules/` | 永久，随代码同步 | [模块入口](templates/module-overview.md)、[主题文档](templates/module-topic.md) |
| 设计文档 | 记录一次设计的讨论：目标、候选、选型结论与开放问题 | `.agents/docs/design/` | 一次性产物 | [设计文档](templates/design-doc.md) |
| 开发文档 | 记录一次开发的落地：目标、改动落点与代码锚点，给人读 | `.agents/docs/dev/` | 一次性产物 | [开发文档](templates/dev-doc.md) |
| roadmap 与迭代计划 | 当前迭代的任务状态、执行记录 | `.agents/docs/iteration/` | 迭代收口清空 | [roadmap 模板](templates/roadmap-template.md)；[迭代计划](templates/plan-template.md) |

一次性产物指为特定目的写作一次、不入库，对应任务入版后可清理。
用户指定保存路径时，按用户路径落位。

## 模块文档

模块文档维护模块的定位、边界、契约、关键入口与当前事实；深层机制和长示例下沉到同目录主题文档。
小模块使用 `.agents/docs/modules/module-<模块>.md`；大模块或文档达到 500 行时拆为
`.agents/docs/modules/<模块>/overview.md` 与同目录主题文档，overview 作为唯一对外入口，并索引各主题文档。
模块文档只保留当前仓库的唯一事实，历史状态、日期等信息只留版本控制。

入口章节沿用六章；信息不足的章节简述现状：

```text
一、定位与边界
二、设计与机制
三、迭代操作
四、关键约束
五、环境坑
六、已知缺陷与方向
```

各章按模板展开，写法要点：

- **定位与边界**：说明职责、目标目录和依赖边；同层直接依赖/被依赖各一行链接，跨层关系指向架构总览。
- **设计与机制**：给当前设计摘要、API 契约与主题索引。
- **迭代操作**：给构建、运行、验证等常用操作与命令。
- **关键约束**：记录使用本模块必须遵守的设计约束——不变量、契约前置条件、线程与生命周期规则、容量与性能边界；
  每条写清约束内容、来源依据和违反后果，随代码演进同步更新。
- **环境坑**：记录设备环境因素带来的适用条件与处置，覆盖平台、驱动、编译器等。这条只有无法避免时才写，要尽可能通过流程规避。
- **已知缺陷与方向**：记录真实且尚未解决的缺陷、当前不支持的能力与远期方向。

## 设计文档与开发文档

两类均为一次性产物，面向人类读者，核心要求是易于人类理解：

- 叙述完整：给足背景、动机与推导过程，关键内容用完整段落陈述，读者单独阅读即可跟上。
- 信息充实：覆盖读者从零理解所需的背景、术语、依赖与示例，按理解顺序组织。
- 表达自然：以通顺陈述为主，列表与表格用于并列信息，保留必要的细节与特例说明。
- 落到代码：给出与代码现状的对应关系——模块、入口、锚点，便于读者定位验证。

两类是一条链，不是并列的两种写法：

- **设计文档是讨论**：承载发散到收敛——背景与目标、现状与差距、候选方案与权衡、选定方案与理由、风险与开放问题。
  允许未定稿，用状态标注；讨论产出的结论（选什么、放弃什么、还有什么没定）是开发文档的输入。
- **开发文档是落地**：只写定稿后的实施内容——目标行为、改动落点与代码锚点、实施顺序、验收方式。
  选型理由一句带过并链接设计文档，不复述权衡与候选对比；没有对应设计文档时，用两三句交代为什么走这条路。

开发文档的“现状”只作改动落点的锚点清单，不做差距论证；差距与取舍一旦在两类文档各写一遍就会漂移。
无实质选型分歧的改动（单一路径、影响面单一、可随时回退）不写设计文档，结论直接进开发文档。
关键位置落到代码锚点（`path:line` + 符号名），注明代码快照，行号漂移后以代码为准。

开发文档通常与 roadmap 一起出现，两者的读者与写法固定分工：

- roadmap 及迭代计划是给 agent 看的，描述状态与任务路径，可以简写，只引用任务 ID 与结论。
- 开发文档是给人看的，讲清目标、方案与改动落点，易理解最重要：给足上下文与推导，
  读者不依赖其他文档即可独立理解；设计取舍在设计文档里论证过就引用，不重复展开。

## roadmap 与迭代计划

- roadmap 是一份可执行的开发计划：任务拆到可独立编译验收的粒度，标明依赖与顺序，
  接到任一 pending 任务即可开工，不需要再补上下文。它是当前迭代唯一的状态载体。
- 读者是 agent，写法以事实与操作面为主：任务 ID、一句话目标、依赖、状态、轮次、结论、
  可直接复制的验证命令。设计理由与方案细节留在开发文档，这里用任务 ID 关联而不复述。
- 决策随状态一起登记：未拍板的决策点进决策表并给出建议，拍板后回填结论与日期；
  执行记录按轮登记结果与验证入口，出现意外情况写进备注。
- 迭代计划承载同一迭代的静态部分：需求拆解、依赖关系、设计基线、代码锚点、验收明细与风险，
  实施前写定，后续只回写形状级变更；两个文件用任务 ID 对齐。
- 生命周期：当前迭代为空或用户明确要求替换时初始化；执行中插入或追加任务直接更新本文件，
  沿用已有规划；迭代收口删除计划文档并把 roadmap 重置为空模板，历史留 Git，机制沉淀到模块文档。
- 模板见 [roadmap 模板](templates/roadmap-template.md) 与 [迭代计划](templates/plan-template.md)；
  规划流程按 `complex-task-planning` skill，执行与状态流转按 `development-workflow` skill。
