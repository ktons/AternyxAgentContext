# 开发执行流程

- 执行用户明确指定的已有 roadmap；普通开发按工作区规则推进，不套用本流程。
- 开发文档中还有未拍板的关键决策时，先提醒用户；用户要求继续执行时按开发文档的建议落定。
- 尽可能完成 roadmap，执行中按工程惯例与主流做法自行决策，并把决策纳入汇报。
- 依赖其他平台环境的任务标记为“无法验证”，在模块文档登记为远期事宜并告知用户，其余任务照常收口。

## 角色与调度

- 主 agent 负责范围、派发、关键 diff 与证据审查、状态、Git 和交付；实现子 agent 负责实现、自验证、
  模块文档同步与摘要，按主 agent 的派发领取任务。只读 agent 提供事实、风险和证据。
- 同一工作区的实现与修复串行，独立只读工作并行；构建、GPU、运行实例统一调度。
  每次派发（含失败/中断接手与修复）使用新子 agent，保持上下文干净。
- 构建、全量测试及已知长任务后台运行，保留日志和结果入口，主会话保持响应。

## 执行循环

1. **明确任务**：核对最新指令、分支、已有改动和依赖，领取当前迭代中依赖已满足的 pending 任务，按依赖和 ID 推进。
2. **信息收集**：收集实现所需信息，精确到代码行号，减少子 agent 的重复摸底；按架构入口 → 相关模块文档 → 必要源码的顺序阅读。
3. **派发**：内联目标、边界、约束、已知结论、代码锚点、现状和验收；[派发与交接模板](references/task-brief.md) 按需裁剪。
4. **实现与自验证**：完整增量尽量可独立编译验收。按项目入口编译受影响目标、运行相关测试；
   行为中性/回归敏感改动补目标证据（中性渲染做逐帧对比），图形效果迭代用固定口径出图 + 指标/目检
   作中间判据，纯文档任务检查差异、引用和规则。开发期允许中间态失败：记录失败项、现场与原因后
   继续推进，既有失败与环境失败不阻断。涉及 C++ 数学任务时尽量降低 ulp，4~8 ulp 作参考范围而非硬门槛。
5. **审查与验收**：单项任务由主 agent 核对范围、关键 diff、知识同步和验证输出；整轮迭代完成后派新的独立只读
   reviewer 做最终收尾与查缺补漏。缺证据先补，未验证项明确标注，语义审查与测试结果并重，通过项按需复跑。
6. **登记与提交**：每个通过验收的完整增量更新 roadmap 状态与执行记录，再由主 agent 按工作区规则提交。
   提交只含代码与入库文档（架构总览、模块文档）；临时文档在 `.agents/docs/temp/`，不入库。
   未过验收的任务派新的子 agent 继续迭代。提交保留在本地，分支与合并由用户发起。
7. **续作或收口**：未完部分带现状交新 agent；完成时确认自起进程已回收，按 `documentation-writing` 的
   生命周期清理本期临时文档并重置 roadmap，再回报变更、验证、提交与遗留。
8. **文档沉淀**：把模块机制、契约与缺陷同步到模块文档，模块清单与依赖关系变化同步架构总览，
   工具经验更新到对应 references，可由子 agent 迭代时完成；写法按 `documentation-writing`。

## roadmap 与迭代文档

- `.agents/docs/temp/roadmap.md` 是当前迭代的执行表，同目录的 `iteration-<主题>.md` 保存目标、每阶段验收、
  执行细节与风险；两份合起来自包含，执行时不引用开发文档与设计文档。
- 字段、状态枚举、初始化与重置规则见 roadmap 模板与 `documentation-writing`；本 skill 只规定执行中的动作：
  新任务登记进 roadmap 并把执行细节与验收判据补进迭代文档，执行记录按轮写入。

## 失败与中断

- 出现 crash、停滞、证据矛盾时保留现场，串行派专项新 agent 排查，分别按 `win-crash-debug` 与
  `graphics-debug-methodology` 处理。
- 单次任务子 agent 派发设置 90 分钟后台定时；超时按任务失败处理（常见于子 agent 注意力耗尽），
  发消息要求其停止并交接，之后派新的子 agent 继续实现。
- 单项任务连续三次派发仍未完成时，由主 agent 判断问题复杂度；确认无法解决则中断整轮迭代，
  向用户详细汇报问题，把后续预算留给可推进的任务。
- 用户取消后保留交接并停止；用户明确授权开发后恢复，恢复后持续推进剩余任务。
