# 开发计划与开发文档

把“改什么、怎么改、怎么验”写成一份可以照着执行的开发文档，落位 `.agents/docs/dev/`。

本指令独立：不要求已有设计文档或 roadmap，读者只读本文即可接手实现。

## 流程

1. **确认目标**：目标行为、非目标与边界；有歧义先向用户确认。
2. **勘察现状**：定位相关模块、入口、数据结构与调用链，记录 `path:line` 与符号名；
   按架构入口 → 模块文档 → 必要源码的顺序读，不靠通读源码重推已有设计。
3. **定改动落点**：列出将被改的文件、符号与新增位置，标出可照抄的现有先例；
   不确定的先读代码确认，不写“大概在某个模块”。
4. **排步骤**：按可独立验证的增量排序，写清每步改什么、为什么这个顺序、做完后系统处于什么状态；
   依赖顺序、并行边界与相邻改动的冲突点写明。
5. **定验收与回退**：每步给可复制命令、预期输出或观察点；不可逆改动给回退方式；
   当前环境无法验证的项注明依据与替代判据。
6. **落文档**：按模板写，缺信息就补勘察，不把问题留给执行者猜。

## 内容目标（必含）

- 目标行为：做完是什么样、如何判定。
- 改动落点：文件/符号/行号锚点，注明代码快照（行号漂移以代码为准）。
- 实施步骤：顺序、每步范围、完成后的状态。
- 验收方式：可复制命令与预期输出，必要时给行为证据口径。
- 风险与回退：影响面、回退手段、无法验证项。

## 边界

- 独立成篇：不引用设计文档、roadmap 与迭代文档；需要方案论证就补两三句理由，不要求读者跳转。
- 不写任务状态与执行记录，那是 roadmap 的事；也不写每阶段验收表，那是迭代文档的事。
- 模板见 [开发文档模板](../documentation-writing/templates/dev-doc.md)，落位与共同写法见 `documentation-writing` skill。
