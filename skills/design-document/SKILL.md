# 方案设计与设计文档

先定义问题，再调研同类成熟实现，最后收敛到推荐方案；产出是一份自包含的设计文档。

本 skill 独立调用：不要求已有开发文档或 roadmap，也不替用户排任务。
落位、文件名、生命周期与通用写法见 `documentation-writing`，本文只规定设计文档的流程与必含内容。

## 流程

1. **定义问题**：目标、约束、成功标准与影响面；歧义先向用户确认，不替用户假设。
2. **调研成熟实现**：至少对照两个可信实现（主流引擎、开源项目、同类产品），记录出处与版本、
   它的做法、成立条件，以及为什么这么做；找不到先例时说明依据不足，改用原理推导。
3. **列候选**：含“照搬成熟做法”“按现状改造”“不做/延后”，给统一对比维度
   （改动面、风险、性能、维护成本、可逆性）。
4. **权衡与推荐**：逐维度比较后给推荐与理由，写清放弃了什么、代价是什么；
   避免“两个都可以”这类没有结论的收尾。
5. **落文档**：按模板章节写；信息不足的章节标“待确认”并在会话说明，不编造调研结论。

## 文档结构（按模板七节，必含）

1. 背景与目标：为什么做、面向谁、成功标准与边界。
2. 现状与差距：当前实现与 `path:line` 锚点，以及与目标的差距、哪些必须这次解决。
3. 成熟实现调研：至少两个可信实现，出处、做法、适用条件、可借鉴与不可照搬之处。
4. 候选方案与权衡：候选、做法、代价与风险，统一维度对比。
5. 选定方案：整体形状、关键接口与数据归属、生命周期、依赖顺序；分阶段时给划分依据与放弃的选项。
6. 改动面与依托：受影响的模块、入口与上游依赖，写到模块与入口级。
7. 风险与未决：已知风险与缓解；未拍板问题给候选、当前倾向与建议。

## 边界

- 实施步骤、文件级改动清单与验收属开发文档，本文不写；改动面只到模块与入口级。
- 决策在本文收口：不引用开发文档或 roadmap，事实依据只引用架构总览与模块文档。
