# 方案设计与设计文档

先定义问题，再调研同类成熟实现，最后收敛到推荐方案。产出是一份自包含的设计文档，落位 `.agents/docs/design/`。

本指令独立：不要求已有开发文档或 roadmap，也不要替用户排任务。

## 流程

1. **定义问题**：目标、约束、成功标准与影响面；歧义先向用户确认，不替用户假设。
2. **调研成熟实现**：至少对照 2 个可信实现（主流引擎、开源项目、同类产品），记录出处与版本、
   它的做法、成立条件，以及为什么这么做。重点看取舍逻辑，不是抄接口；找不到先例时说明依据不足，改用原理推导。
3. **列候选**：候选含“照搬成熟做法”“按现状改造”“不做/延后”，给出统一对比维度
   （改动面、风险、性能、维护成本、可逆性）。
4. **权衡与推荐**：逐维度比较后给推荐与理由，写清放弃了什么、代价是什么；
   避免“两个都可以”这类没有结论的收尾。
5. **落文档**：按模板写；信息不足的章节标“待确认”并在会话说明，不编造调研结论。

## 内容目标（必含）

- 问题与目标：面向什么场景、成功标准、边界。
- 成熟实现调研：谁这么做过、做法、适用条件、可借鉴与不可照搬之处。
- 候选与权衡：至少两个候选，统一维度对比，结论明确。
- 推荐方案：选定方案、理由、放弃的选项与代价。
- 风险与未决：风险、前置假设、需要用户拍板的问题。

## 边界

- 本文自包含：结论与取舍都在本文，不引用尚不存在的开发文档或 roadmap。
- 实施步骤、代码改动清单与验收属开发文档，本文不写。
- 模板见 [设计文档模板](../documentation-writing/templates/design-doc.md)，落位与共同写法见 `documentation-writing` skill。
